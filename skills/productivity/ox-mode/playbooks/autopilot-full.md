### Autopilot-full

**T3 Code only.** Owners are launched threads that outlive this session, watched and audited on a schedule.

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in the Shipping playbook can carry a verdict across a rebase, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Start one owner per PR, and keep its work where a replacement can find it.** GitHub CLI (`gh`) is the forge. Each owner is a `t3_thread_launch` thread on its own branch with a worktree `workspaceStrategy` off the default branch, its brief opening with the text of `SUBAGENT-PREAMBLE.md`, its placeholder replaced by the absolute path of ox-mode's `SKILL.md`. Commit first, because uncommitted edits do not reach a new worktree. The owner builds, opens its PR per Opening a PR, proves the change on the real artifact, babysits to green per Babysit, and merges once steps 4 and 5 clear it.

   Open the PR early so CI and review bots run alongside the work. The code is ready only after `deslop` and `no-comments`, so the full swarm runs on finished code. Then rebase onto the current default branch and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless the default branch conflicts or breaks CI, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume the thread dies. Soon after starting, push and start a decision trail per `show-me-your-work` in the root's store at `~/.local/state/ox/orchestrate/<project-slug>/trails/`, outside any worktree, then push after every unit worth keeping. Whoever starts a subagent records its task or thread id, state, and a stuck-after runtime in that store, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off the default branch, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. Fan out independent verifiers at the code-ready SHA per `swarm`, on the `review` role. They re-run the checks, prove the load-bearing behavior with what they can run (ox-mode's Non-negotiables), and audit the diff. The verdict is not clean before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Send every proven finding, whatever a lane labeled it, to the owner in one fix-forward, with a red test or check across every site with the same defect. A defect the default branch shows without the PR is recorded against it and does not gate the PR, but one the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead.
5. **The owner merges only what you verified, tested on the branch it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto the current default branch, reports the new head, and waits for green CI.

   Right before merging, fetch the default branch and ask whether its changes can affect the patch, because rebasing for every move never ends. Rebase and wait for CI when the code that would land was never tested together: a conflict, a file both sides changed, or a change to which checks run. When the default branch changed a caller of the patch or something the patch depends on, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If the default branch would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work. The owner calls `unwatch_pull_request` before it reports, and at handoff the root clears any remaining watch with `unwatch_pull_request` passing the owner's `threadId`.
6. **Run the root layer.** Anything that loosens a gate, such as a raised limit or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces.

   On the operator's go, arm `schedule_task` with `{"type":"interval","everyMs":3600000}`, bound to this root thread, with a prompt that runs this audit, until no delegated work is left, because long runs drift and agents stall silently. Each tick re-reads this playbook and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it. It probes every agent, down to the leaf lanes (`t3_thread_list` with `includeSubagents: true`, `t3_thread_read`, and each owner's `task_status` on its own children), and judges each by its side effects, because status text can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once. A tick that changed something for the operator ends with a short catch-up message, and one that changed nothing stays quiet. End the cadence with `delete_scheduled_task` once no delegated work is left.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order, and the root pauses the audit schedule with `update_scheduled_task` (`enabled: false`). Each owner reports where it stands and keeps its brief until the operator releases it, and the release re-enables the schedule.

**Reply:** catch the operator up on what changed since their last look, newest first: each PR's state and verdict, what merged, countersigns and why, and open operator gates, with links to each PR and the trails.
